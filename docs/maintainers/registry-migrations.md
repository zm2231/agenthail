# Registry migrations

`registry.Open` first reads `PRAGMA user_version` and `PRAGMA journal_mode` on a read connection. A database at `schemaVersion` in WAL mode is opened as it is, without the write lock: every CLI command opens the registry, and one that queued for the write lock behind the daemon and other commands could wait past the 15 s `busy_timeout` and fail with `database is locked`. Under contention from 128 processes, each opening and writing 15 times next to a process that holds 40 ms write transactions, opening through the migration failed this way, while the read-only open ran every command. A database at `schemaVersion` therefore has to hold exactly the schema and data a build of that version produces; see step 1 below.

Any other database is brought to the current schema in one transaction (`migrate` in `internal/registry/registry.go`). The connection uses `_txlock=immediate`, so the migration holds the write lock from its first statement. `migrate` reads `user_version` again under the lock and leaves a database another opener has just brought to `schemaVersion` as it is. Otherwise `migrateTx` runs every step on that transaction, and `user_version=schemaVersion` is written once, as the last statement. If any step fails, the database keeps its previous schema and version.

Before migrating a database that is already below `schemaVersion` (version 1 or more), `migrate` copies it to `registry-before-v<N>.db` beside it, where N is the schema it is about to reach. The copy runs under the migration's write lock: `migrate` reads `user_version` on its transaction, then copies its pages to a mode-0600 temporary file with SQLite's backup API on a separate connection, takes the copy out of WAL mode so it is one self-contained file, checks the copy's `user_version` matches, and renames it into place. A concurrent opener therefore cannot name an already-migrated copy "before". If the copy fails, the migration is refused and the database keeps its schema. Only the two newest copies are kept.

After the migration commits, outside the write lock, the same open compresses every plain copy to `registry-before-v<N>.db.zst` (mode 0600): it writes a temporary file, syncs it, renames it and then deletes the plain copy. A 444 MB registry compresses to 83 MB in about 1.6 s and blocks nothing. A crash at any step leaves a usable copy, and the next upgrade finishes the job; if compression fails, the plain copy stays, the migration stands, and `daemon.log` says so. Taking a new copy for a schema first removes any compressed copy for that schema, because a restore leaves its copy in place and the new copy is the newer one.

Other opens wait on the write lock for up to `busy_timeout` (15 s), so the copy must stay well under it, and the daemon cannot report ready until it finishes. A page copy of a 437 MB registry takes 1.4 to 3.8 s at a load average near 37; `VACUUM INTO`, which rebuilds every table and index, took 7.5 to 19 s on the same registry. The daemon logs what each start spent in `daemon.log`: `registry open took`, `registry migrated from schema N to M: backup …, migration …, compress …`, and `started; … after launch`.

A new registry is created with `auto_vacuum=INCREMENTAL`, and the daemon gives freed pages back to the disk after each journal sweep. An existing registry keeps its mode, since changing it takes a VACUUM. VACUUM blocks writers for as long as it runs and they give up after `busy_timeout`: measured at load 9-14, 6.3 s at 443 MB, past 15 s at 1.1 GB with failed writes. So an existing file is never converted, and its freed pages are reused for new rows instead.

A migration that reads `session_journal.payload` as JSON must handle `payload_codec`, or restrict itself to message and text rows, which are always plain.

A database stamped newer than `schemaVersion` was migrated by a newer agenthail. `migrate` reads the stamp first, under the write lock, and `Open` returns `*NewerSchemaError` ("registry is schema N; this agenthail supports M; install a newer agenthail") without writing to the file. When a copy for schema N exists beside it, in either form, with a schema this build supports, the error also gives the steps to go back to it: `agenthail daemon stop; agenthail registry restore <N>; agenthail daemon start`. A compressed copy's schema comes from the SQLite header at the start of its stream.

`agenthail registry restore <N>` is run by the build that refused, which is older than the registry, so it never opens the registry through `Open`. It holds the daemon's lock, so it refuses while a daemon runs and a daemon cannot start until it finishes. It also needs `registry.db.lock` exclusively. Every open holds that file shared until `Close`, so a daemon a service manager respawns, or a CLI command, waits rather than reading the registry mid-swap, and no process that opened the registry earlier can be left writing to the file a restore sets aside. If the lock isn't free within ten seconds, the restore refuses and says to stop the agenthail command holding it. It writes the copy to a temporary file and checks its `user_version` and `PRAGMA quick_check`. Only then does it hard-link the current registry and its `-wal`, `-shm` and `-journal` to `registry-v<N>.db*` (never over an earlier one), unlink those sidecars from the registry path, and rename the copy over the registry. The order matters. The registry path never goes missing, because an opener would create an empty registry there. The sidecars leave before the rename, because SQLite applies an old WAL to whatever file it finds and the result reads as `database disk image is malformed`. Every original stays reachable through its link at every step, so a failure only relinks and never deletes the last name of a file.

Both locks are `flock`s on open files, so the kernel drops them when the process dies, however it dies, and the lock file itself blocks nothing. It is close-on-exec, so a process the daemon spawns does not keep it, and it is opened without following a symlink. An open that cannot take the lock fails, since nothing would then keep a restore out, and the error names the file and the `chown` that fixes it. An open waits at most two minutes for a restore and then fails; `daemon-run` takes the daemon lock before it opens the registry, so during a restore it exits at once and its service manager starts it again. Before linking, the restore opens the registry with the plain driver, without `Open` or a schema check, and runs `PRAGMA wal_checkpoint(TRUNCATE)`, so the WAL normally holds nothing by the time it is unlinked. If that fails, for example because the file is read-only, the restore carries on. In that case a kill between the unlink and the rename leaves the old main file without its WAL: the registry opens, but the rows only the WAL held are in the `registry-v<N>.db` set beside it. Running the restore again finishes the job. The copy stays, so a restore can be repeated. With no N, the command lists the copies. A build from before compressed copies cannot read a `.zst`; going back past that point means decompressing with `zstd -d`, moving the registry aside and putting the copy in its place by hand.

Every `agenthail` command, an open and a restore refuse to run as root when the registry's directory or the one above it belongs to someone else, which is what `sudo agenthail` with a preserved HOME looks like: "don't run agenthail with sudo; run it as <owner>". The command refuses first, before creating anything, because a directory, database, lock or config file left root-owned there locks its person out. A server or container whose HOME is root's own carries on, and so does root with an empty or relative HOME, such as a system service with no `User=`: only an absolute path owned by someone else refuses. The packages and `agenthail-uninstall` run agenthail as the person (`sudo -u <person> env HOME=…`), and Homebrew runs it as the installing user.

The connection pragmas set before it change nothing on disk; WAL mode, which does, is set only after `migrate` accepts the schema, so a refused registry keeps its journal mode. The CLI and `daemon-run` exit with that error instead of running against tables this build does not know.

The CLI opens the registry only when a command first needs it (`App.registry` in `internal/cli/cli.go`), so `--help`, `version` and argument errors never create or migrate one. `cmd/agenthail` opens the registry in the home directory with `registry.OpenDefault(mayUpgradeRegistry(version))`. A build without a stamped version (`go run` or a plain `go build`, where `main.version` is `dev`) creates a new registry but refuses to migrate an existing one with `*DevUpgradeError`, because the installed agenthail would then refuse the branch schema. Run a branch build with a scratch `HOME`, or set `AGENTHAIL_ALLOW_DEV_MIGRATION=1` to migrate anyway (the copy above is taken first). `registry.Open` with an explicit path, as tests use, always migrates. Release packages and `install.sh` stamp a version (`install.sh` uses `git describe`, or `source` outside a Git checkout), so installed builds migrate.

A new database runs the same path with version 0. Because the `schema` constant declares every table and column, a new database needs no `ALTER TABLE`.

## Adding a schema change

1. **Version.** Every change to the `schema` constant or to `migrateTx`, including a column, an index, a trigger or a data step, raises `schemaVersion` to the next unused number N. A database already at a version is never migrated again, so a change shipped without a new version never reaches it. If another branch takes N on `main` first, merge `main`, move to N+1, and update your gate and tests to match. Then regenerate `internal/registry/testdata/schema.sql` with `AGENTHAIL_UPDATE_SCHEMA=1 go test ./internal/registry -run TestTheSchemaChangesOnlyWithItsVersion`; never edit it by hand.

2. **New table.** Add `CREATE TABLE IF NOT EXISTS` to the `schema` constant. The constant runs on every migration, so existing databases get the table too. Indexes on the new table also go in the constant.

3. **New column on an existing table.** Do both:
   - add the column to that table's `CREATE TABLE` in the `schema` constant;
   - add `ensureColumn(tx, table, column, declaration)` in `migrateTx` with the same declaration.

   The default must be a constant. `ALTER TABLE` cannot add a column whose default is an expression such as `datetime('now')`.

4. **Index on a new column of an existing table.** Put `CREATE INDEX IF NOT EXISTS` in `migrateTx` after that column's `ensureColumn`, without a version gate, so a database several versions behind gets it too. Do not put it in the `schema` constant. The constant runs before `ensureColumn`, so on an older database the column does not exist yet and the index would fail. If the index depends on values a data step fills in (a unique index over a backfilled column, for example), put it after that step: before the backfill, existing rows all hold the column's constant default and a unique index would fail.

5. **Data step** (backfill, rewrite, dropping a column). Write a function that takes `tx *sql.Tx`. Call it from `migrateTx` inside `if version < N { ... }`, after any `ensureColumn` it depends on. The step:
   - runs only on `tx`: never `r.db`, never its own `Begin` or `Commit`, never `PRAGMA user_version`;
   - must be correct on a new database, where version 0 runs every gated step against empty tables;
   - should be safe to repeat. For example, `dropQueueExpiry` checks with `columnExists` before it drops anything.

   A step without a gate runs on every migration (`recordRuntimeKinds` is one). Use that only when the step is idempotent and cheap. No step runs on an open of a current database, so an invariant the running code needs must be kept by the code that writes the rows, not repaired by a later open.

6. **Version gate.** Gates compare with `version < N`, never equality, so a database several versions behind runs every step it missed, in order. A database stamped newer than `schemaVersion` never reaches the gates: `Open` refuses it first.

7. **Session view inputs.** A table a session view reads is listed in `presentationInputs` (`catalog_presentation_version.go`), and its triggers move the presentation version that keys cached views. `migrateTx` drops those triggers before its first step and creates them after its last, so they name the columns the tables end with and never keep a step from dropping a column. An update moves the version only when a watched value changes, so a writer that rewrites a row on every poll keeps cached views. List the columns the view reads; a table without a list watches all of its columns. Any other trigger that writes a view input on update must also fire only on a change. A test that drops a column to stand in for an older schema calls `asBeforePresentationTriggers` first, since no older registry had these triggers.

## Tests

- `TestTheSchemaChangesOnlyWithItsVersion` compares the schema of a new registry with `testdata/schema.sql`, which records it for one `schemaVersion`. It fails when the schema changes without a new version, and when the version changes without regenerating the file.
- `TestOpeningACurrentRegistryWaitsForNoWriter` holds the write lock on another connection and requires `Open` of a current registry to return without waiting for it.
- `TestSchemaDeclaresEveryColumn` builds a database from the `schema` constant alone and compares its columns with a registry from `Open`. It fails when a column reaches new databases only through `ensureColumn`.
- `TestOpenRefusesARegistryANewerAgenthailMigrated` stamps a registry past `schemaVersion`, in WAL and in rollback-journal mode, and requires `Open` to return `*NewerSchemaError` and leave the database and its journals byte for byte unchanged. `TestOpenWaitingOnANewerAgenthailsMigrationRefusesItsSchema` has a newer build stamp the registry while `Open` waits on its lock.
- `TestAMigrationKeepsACopyOfTheRegistryFromBeforeIt`, `TestARegistryThatCannotBeBackedUpIsNotMigrated`, `TestANewerSchemaRefusalNamesTheCopyFromBeforeItAndHowToRestoreIt` (which runs the printed restore steps through `/bin/sh` in a directory whose name has spaces, quotes, `$` and a backslash) and `TestADevelopmentBuildCreatesButDoesNotUpgradeTheDefaultRegistry` cover the copy, its refusal and the development-build guard.
- `TestOpenMigratesHistoricalSchemas` upgrades every fixture in `internal/registry/testdata/migrations` (written by `generate.sh`). `assertSchemaMatchesFreshRegistry` then requires the same columns, declarations and indexes as a new registry.
- `TestEveryHistoricalRegistryEndsWithTheTriggersAFreshOneHas` requires every historical fixture to end with the same presentation triggers as a new registry. `TestEveryRegistryValueThatChangesASessionViewMovesItsCacheKey` (in `internal/daemon`) requires every view input's row to move the cache key when a value the view shows changes, and to leave it when the row is rewritten with the values it has.
- Each data step needs a test that seeds a registry at version N-1 with the old shape and rows, opens it, and checks the result. Existing examples are `TestSchema14RekeysClaudeRowsToTheirConversation` with `seedVersion13`, and `TestOpenRetiresQueueExpiryLeftOnARegistryAtTheVersionBefore`.
