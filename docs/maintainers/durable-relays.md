# Durable relay handoffs

Create a relay with `agenthail relay add <from> <to> [regex] [--once] [--when turn_finished|goal_completed]`. The same `handoff` values are accepted by the `relay-add` dashboard/API action and exposed in native controls.

- `turn_finished` evaluates every captured successful completion in source order.
- `goal_completed` waits for an explicit provider goal with status `complete`, a creation time, and a finished final turn whose provider completion timestamp is at or after goal creation. Missing completion timestamps keep the route waiting. It evaluates the latest pending completion and consumes earlier intermediate results with it. Missing, active, paused, blocked, limited, or unreadable goal state keeps the route waiting. The completed goal's creation time and objective identify the handoff; repeated observations do not fire it again.
- Regex filtering applies after the handoff condition. A one-shot route becomes inactive only when its matching handoff is durably queued.

Route creation first checkpoints the source and excludes existing history. Upgraded routes establish their first checkpoint on the first daemon scan. Claude resumes from a durable JSONL byte offset and partial-turn state; Codex walks turn and item pages back to its saved provider turn; Notion retains ordered inference-message identities. Capture commits all returned events and the next provider cursor together. A failed capture retries the previous position.

Each route consumes the retained completion log independently. Enqueue, delivery intent, receipt, cursor advancement and one-shot deactivation share one SQLite transaction. A failed transaction rolls everything back. The daemon can consume persisted events even when a subsequent source read fails. Goal routes wait for a successful source read and goal lookup so they cannot release an outdated partial view.

Hop counts come from the originating queue row. The relay envelope `[agenthail relay hops=N id=<route> turn=<completion> source=<name>]` names the route and source completion ahead of the free-text source label; they identify that row by its `relay:<route>:<completion>` delivery key. The first captured input/completion in the receiving session that carries the envelope is bound to the row; a raw hop prefix, an envelope with no matching row for that session, or an envelope copied into a later input does not inherit relay hops.

`relay list --json` returns `handoff`, `eventCursor`, `pendingCount`, and `lastError`. The dashboard/native controls show the condition, pending count and errors. Pending counts refer to events not yet evaluated by the route, including intermediate events waiting on a goal. `fireCount` counts durable enqueues, not remote delivery. Inspect the delivery queue and history for transport acceptance, completion evidence, expiry, or failure.

When an exited Claude row is absorbed into a live row of the same conversation, its routes, checkpoint and unread completions move with it. If the live row already captures that transcript for its own relays, the exited row stays until its active routes are spent or removed: the two rows read the transcript independently, so one log cannot carry the other's route positions. Active routes are not automatically deleted when a conversation goes offline. Queued handoffs retain the ordinary one-hour expiry and operator retry/cancel behavior. Relay failures record a delivery problem without injecting a failure message into the source conversation. This prevents the source's reply from becoming another relay.

If a saved provider boundary is missing, or a Claude transcript is truncated/replaced before its checkpoint, capture stops with a visible route error. Restore the provider history to resume without loss. To deliberately abandon the unread backlog, remove every route from that source and create new ones. Removing the last route clears the source checkpoint; the next creation baselines the provider again. Other routes from that source keep their shared checkpoint. Do not discard the registry to hide a gap. Completion history remains in the registry until its source session is removed; it is not subject to the UI journal's bounded retention.

Local verification uses temporary registries, transcript files, deterministic provider transports and an outbox receiver. It proves capture, rollback, restart, ordering, deduplication and consumer fields without sending work to live agents. Remote provider delivery and power-loss durability are separate boundaries; this uses the registry's existing WAL/synchronous settings.
