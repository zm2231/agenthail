# Daemon-owned session presentation

The daemon owns session-list scopes, counts, ordering and display text, and every client renders what it sends. The first step implements the explicit-scope snapshot and the CLI list; the remaining client steps are a release plan, not a claim that those clients have migrated.

## Release sequence

1. PR1: canonical scoped snapshot, CLI `list`, this design. Unscoped snapshots, federation snapshots, existing child pages, streams, and old count fields retain their existing contracts. No fallback decoder is added.
2. PR2: migrate dashboard rendering and delete its policy helpers. Complete non-session dashboard metadata integration and shared detail/search/provider-link display producers needed by the browser; scoped PR1 responses contain session-view data only.
3. PR3: shared Swift/Mac/iOS migration below. Mac and daemon ship together; iOS selects one daemon catalog including mirrors, with TestFlight lag accommodated by retaining the unscoped contract. Finish detail presentation positions, serving-authority remote detail, provider-link display, and metadata consumption before native migration ships.
4. PR4, after the PR3 iOS build is released: delete `totalSessions`, old top-level/project count fields and the unscoped UI scope/order/filter paths. Migrate `project list` counters to the canonical planner in this step; preserve the complete federation reconciliation set and explicit child history pages. CLI `list` has no old policy path after PR1.

The full end state below removes client policy. Retention until the named release step is sequencing; new consumers require the new fields and never derive replacements. PR1 does not change Swift or dashboard JS.

## One catalog authority

One visible catalog has one serving daemon, identified by `catalogHostId`, `hostEpoch`, and an opaque `viewRevision`. Its universe is catalog rows from that daemon, including mirrored peers and retired catalog rows. Raw registry-only history is outside it. Hidden subagents remain available through the existing child/detail endpoints. Stale observations stay in the universe; staleness does not mean archived, deleted, or inactive. Preserve `freshness` and `observedAt` unchanged when formatting a view.

iOS selects one serving daemon's catalog, including its mirrors. Keep independent pairings and route fallback for opening a session, but remove merged catalog presentation. Independently paired, mutually unmirrored hosts do not form a combined list. Federation remains a daemon responsibility (`native/iOS/HostCatalog.swift:65` is the client merge being deleted).

## Scope and count semantics

Scope tokens are `running`, `current`, `recent`, `all`, `archived`. The default for CLI, browser, Mac and iOS is **current**, with that same visible name. Add CLI `--recent` and `--running` alongside the existing `--all`/`--archived`; conflicting flags fail. Recent is distinct from Current, rather than keeping the existing alias (`internal/daemon/projects.go:178`).

Determine ancestry once on the complete unfiltered compact catalog, before visibility, scope filtering or paging. Use host-qualified identity and parent links; a delegated row without a reachable valid root does not become a new family. Top-level rows are eligible. A descendant becomes list-eligible if canonical current/recent/running matches it or it is individually archived; retain every necessary ancestor as context. Other inactive descendants remain child/detail history, outside listed-session totals. In particular, do not first apply the existing `CatalogListing.Hidden/Retired` filter: its raw-busy/current test can hide an idle waiting/background/queued child before the canonical policy sees it (`internal/registry/catalog_listing.go:54,77`). Remove that separate UI-list visibility decision; streams invalidate the view rather than deciding its membership. A family's project/checkout is its root's; a matching child brings its ancestry, not a new project count.

- Define predicates on individual listed members first. `working(member)` means raw `busy`, running background work, or an observed working-subagent rollup greater than zero. This drives visibility; it is not the string “Working.”
- `current(member)`: not archived, and either owning-daemon provider presence, working, pending/inflight queued messages, a waiting request, or actionable delivery attention. This forces work and decisions into view even if provider presence is absent. Do not trust an old `currentReason=queued` after the live queue count becomes zero.
- `recent(member)`: not archived, and either current or a nonzero `lastActive >= asOf - 24h`. The boundary is inclusive; a future producer timestamp remains recent. Missing timestamps add nothing. This is the only additional 24-hour list rule.
- `running(member)`: not archived and working.
- `all(member)`: not archived, including offline/retired and stale catalog rows. No raw `Registry.ListSessions` merge.
- `archived(member)`: archived. A family qualifies iff at least one member satisfies both the scope predicate and all explicit member filters. Return qualifying members and necessary ancestry only; ancestry not itself matching is marked `contextOnly`. Thus an individually archived child can appear in Archived without moving its active parent out of Current. The same root identity may occur in both scopes; it is counted once within each, and scope totals must not be added together.

Within a scope, family count means distinct qualifying roots. Session count means distinct qualifying listed rows, excluding context-only ancestry and hidden subagents; queued-message count is separately named. Collapse and pagination never change those totals. Sidebar badges and project headers use family counts and say “conversations”; expanded child rows do not silently change their unit. Counts refer to the same daemon, revision and explicit filters. Different scopes may legitimately have different counts.

## API contract

Extend the existing `/api/v1/snapshot` and browser `/api/state` handler, rather than introduce another list endpoint (`internal/daemon/api_v1.go:92`; `internal/daemon/dashboard.go:323`). PR1 explicit-scope responses are a session-view envelope. PR2/PR3 must integrate non-session metadata before migrating their dashboard consumers; the unscoped envelope remains intact meanwhile.

PR1 request: required explicit `scope` (CLI sends current by default), existing `projectId`/`q`, plus `surface`, `status` (display kind), `attention=1` (only members with actionable attention), `selectedId`, `limit` and `cursor`. `q` is trimmed case-insensitive substring matching of title/name/alias, agent nickname, surface, project name, checkout path/branch and host name. A family matches refinements if the same qualifying member satisfies the supplied member filters. Apply project/refinements before scope counts and collapse. Search does not re-rank the result. Return the normalized request in `view.filters`.

Required response fields:

| Field | Exact meaning |
| --- | --- |
| `view.catalogHostId`, `view.revision`, `view.asOf`, `view.refreshAt` | Authority; opaque revision binding epoch/catalog position, relevant auxiliary state, filters and presentation time boundaries; UTC evaluation time; earliest future recency/quiet/limit boundary requiring refetch, or null. Keep existing `hostEpoch`/`catalogSeq` for transport. |
| `presentationPosition` | On scoped snapshot in PR1; `/session` follows in PR2/PR3: `{hostId, epoch, sequence}`. Epoch is a random daemon-start presentation epoch; sequence is assigned monotonically when the coherent read is captured, serialized with capture, not when the response completes. It orders presentations only within that host/epoch. Cached responses keep their position. A new epoch requires full replacement; never order opaque `view.revision` strings or compare different hosts. |
| `view.scope`, `view.filters` | Effective scope and normalized explicit refinements. |
| `view.counts[scope]` | `{families, sessions}` over the full filtered catalog, before page/collapse. All five scopes are present, including zeroes. |
| `view.summary`, `view.surfaces[]` | Summary contains `queuedMessages` (sum of pending/inflight counts on distinct qualifying members in the active scope) and `attentionFamilies`; each surface entry contains `surface`, its five scope counts and the same summary restricted to that surface. Overview/status-tail/menu consume these fields; `attention=1` supplies the ordered Needs you list. |
| `view.projects[]` | Ordered groups `{id,name,counts,collapsedFamilyIds}` with project identity, `{families,sessions}` counts for the active scope and `collapsedFamilyIds`. Include a deterministic no-project group. Existing project metadata/actions remain available separately. |
| `view.families[]` | Family page in daemon order: `{id, rootId, projectId, checkoutId, members:[{id,depth,contextOnly,pinned}], pinned, workingSubagents}`. Members are compact references in daemon tree order. Member `pinned` is authoritative; a pinned member's ancestors are included as context and loaded automatically. `workingSubagents` counts distinct busy catalog descendants plus provider-observed working subagents that are not catalog descendants, once; never add the already-combined root rollup again. This replaces Swift/CLI rollup rebuilding. |
| `sessions[]` | Hydrated roots of this family page; each contains required `display`. Hydrate members with the same scope/filters plus repeated `sessionId` (at most 200) and required `revision`, without a cursor. This returns the same view metadata, empty `families`, and only requested session rows. Preserve server member order. Existing `parentId` history pages stay separate. Pinned children must be shown/loaded automatically, not hidden behind a closed disclosure. |
| `display` | `{kind,label,detail,waitingPlace,resetsAt,resumesAt,quietSince,toolStartedAt}` on scoped session rows in PR1; every row/detail producer follows in PR2/PR3. `detail` is a string, empty when absent; `waitingPlace` is absent or `agenthail/dialog/terminal/restart/elsewhere`. Kind is for styling, never a source for replacement wording. |
| `nextCursor` | Continuation of family references/root rows under the same authority, revision and filters. `limit` is 1–200 families (default 50), not raw rows. Child `parentId` pages retain a row unit and explicit row total. |

Delete ambiguous top-level `totalSessions` and `counts` in PR4. PR1 retains them; scoped responses report selected matching sessions and family counts respectively, while unscoped semantics stay unchanged. New clients consume only `view.counts`; no fallback alias or optional native decoder defaults for the new contract. `projects[].sessionCount` is replaced by explicit family/session counts computed by this same planner, including `project list` (`internal/cli/projects.go:267`). Count formatting/plurals can stay local; count derivation cannot.

Project order is real projects before no-project, then newest matching family activity descending, then project ID. Within a project, families sort pinned first, then maximum qualifying-member activity descending (missing last), then qualified family ID. Siblings use activity descending then qualified ID; parents precede descendants. Checkout grouping must not re-sort across family order; clients render consecutive checkout bands if needed. A qualifying member is pinned when working, queued, waiting for a request, or carrying actionable delivery attention; a family is pinned iff any qualifying member is pinned. Collapse returns **all pinned families plus the first five unpinned families** in that order. `selectedId` adds its in-scope family without consuming one of five. It never admits an out-of-scope/history row or changes counts. Expansion renders all server-ordered families. More than five pinned families are all visible. `view.projects` covers the complete filtered view, so the client can drain pages until all returned collapsed IDs are hydrated; this can require multiple pages across projects. It must expose loading rather than silently drop unresolved IDs.

## Display policy

One daemon formatter evaluates these rules in order; all clients display its strings verbatim, including accessibility, tooltips and inspectors. Raw status/capabilities remain for interrupt/send/lifecycle behavior.

| Condition (first match wins) | `kind`; label; detail |
| --- | --- |
| Unreachable owning host, or raw unknown/notLoaded | `unavailable`; “Unavailable”; host/observation reason. A local workspace diagnostic alone does not make a functioning session unreachable. |
| Waiting request, even on an idle row | `waiting`; “Waiting on you”; question/input/approval/dialog and where it can be answered. Compute `waitingPlace` once from answerability, dialog, effective stop/resume capabilities, CLI terminal, then elsewhere (precedence currently at `native/AgenthailModels.swift:673`). Respect read-only effective capabilities. |
| Raw busy | `working`; “Working”; quiet note after ten minutes using `lastProgressAt ?? busySince`, plus running tool/no-process evidence. Silence never changes kind. |
| Nonreleased limit-resume record or active usage limit | `limited`; “Usage limit”; waiting uses “Automatic resume scheduled” with `resumesAt`, or “Resumes when the limit lifts”; canceled uses “Stopped; automatic resume canceled”; lapsed uses “Stopped; automatic resume expired”; usage limit without a resume record uses “Limit reset scheduled” with `resetsAt`, or “Reset time unknown”. Released records contribute nothing, as today (`internal/registry/limit_resumes.go:18`; `internal/daemon/limit_resume.go:334`). Busy takes precedence over a leftover limit record. |
| Not busy, running background tasks | `finishing`; “Finishing”; “Waiting on background work”. This is the proposed precise meaning of Finishing, never an inference from quietness. |
| Pending/inflight queue | `queued`; “Queued”; “N messages waiting”. |
| Raw offline | `offline`; “Offline”; empty unless an explicit unavailable diagnostic applies. |
| Otherwise idle | `idle`; “Ready” when open, “Closed” otherwise; empty. `currentReason` is never used as a status label. |

Append “Last observation is stale” to detail when `freshness.stale`, without filtering the row or inventing a fresh observation. Display text contains no formatted time or duration. Exactly four display fields carry instants, encoded RFC3339 UTC and omitted when unavailable: `resetsAt` is an active usage limit's reset (only without a nonreleased resume record); `resumesAt` is a waiting automatic-resume record's nonzero scheduled reset; `quietSince` is last progress, or busy start, once a busy turn has been quiet for ten minutes; `toolStartedAt` is the running tool's nonzero start, only alongside the quiet tool detail. Canceled/lapsed/released resume records expose no `resumesAt`. Waiting and unavailable suppress all clock fields. `view.asOf` and nullable `view.refreshAt` are evaluation/scheduling instants, not display clocks. Clients format only these instants in the viewer locale/timezone. CLI uses the standard system `date` utility (`%x %X`, with inherited locale/TZ), never a shell; a formatting failure returns an error before stdout. JSON retains UTC instants. Queue and working-subagent badges remain separately named facts, not alternate status labels. Attention reasons used for pinning/Needs you are moved from `SessionAttention.build/requestReason` into the daemon and returned as an optional `{kind,reason}` per row; incoming/outgoing delivery decisions retain their own reason even if status is Working. The formatter never overwrites operation capabilities.

## Implementation shape and update consistency

Use small focused files: daemon `session_view.go` for family/scope/order/count planning, `session_display.go` for text, and `session_view_http.go` for request/cursor handling; registry `catalog_view_read.go` for a coherent read; CLI `list_render.go` and a small snapshot request helper; browser `js/session-view.js`. Extract changed pieces from large files; add no narrating comments. The planner, ordering, coherent read and HTTP request handling live in separate focused files.

Registry reads compact facts for the entire catalog, queue/attention/archive/host state and catalog position in one read transaction. Daemon plans selected IDs once while that read is held, then registry hydrates only the root page by ID. Include the fields needed for search and display-kind filters in compact facts. New member hydration uses the same display formatter. Existing child/detail paths migrate in PR2/PR3. After UI migration, remove SQL UI scope/order policy in `catalogPageSQL` and the separate `writeDashboardSnapshot` row filter; SQL fetches selected IDs and data only. Preserve the existing provider presence functions as owning-daemon input rules, not copied client policy. No new database schema or stored display strings are needed.

This replaces the “no Go-side full-catalog scan” promise at `docs/maintainers/catalog-bounded-freshness.md:33`; document the new compact O(N) scan and bounded root hydration. A compact listing scan already exists (`internal/registry/catalog_listing.go:40`). Measure the latency and payload tradeoff on a scratch daemon before shipping; no performance improvement is implied. Compact member references can exceed 200, but full session decoding is at most 200 roots per page; children remain bounded independent pages.

Catalog events become invalidations for the visible view. Clients retain the previous complete view while fetching, then atomically replace rows, descriptors, counts and display. Remove client queue-only list mutations, total reconstruction, and old/new catalog field splicing. Coalesce bursts into one in-flight request plus one dirty retry. Reject a response older than an already-seen catalog position; selection/filter changes carry request identities so old requests cannot overwrite new views. Fetch at daemon `refreshAt` (clients schedule, not derive policy); reconnect/foreground refetches. Cached stale views carry an explicit connection banner and retain their sent status, rather than synthesizing “Unavailable” for each row.

Bind cursors and ETags to the complete view revision, including clock-driven text/scope transitions and auxiliary queue/attention/archive/host changes. The revision excludes per-request sequence and wall-clock time between meaningful boundaries, so unchanged paging remains possible. Child hydration requests carry the parent view revision and the server's member IDs; on mismatch return the existing `catalog_changed` 409 and replace the paged view from page one. Never append root/child pages of different revisions. Selected detail receives the same display and `presentationPosition` in `/session`; accept the newer same-authority presentation as a unit and invalidate its older list view. Do not derive header text from transcript events. Session-stream metadata changes invalidate detail. Search rows include display through the same formatter; create/resume/partial-failure action responses return identity only and require authoritative detail before rendering, avoiding another projection path (`internal/daemon/dashboard.go:2147,2251,2481,2491,2516,2524`).

Remote detail currently passes through `hostRouted` and only gets qualified IDs (`internal/daemon/hosts_api.go:418,472,555`). Change this boundary for session presentation: retain remote transcript/action data, but project catalog/display facts at the serving daemon from its coherent catalog read, exactly as for its list. Keep owner transcript position separate from `presentationPosition`. Mirroring retains source facts and owner identity; the serving daemon formats after effective capability/host resolution, without trusting a peer's formatted strings as policy. A fallback direct-host detail outside this authority cannot overwrite its list or be compared by sequence; switch that detail's explicit authority, show its provenance, and refresh the selected catalog independently. No host is made reachable by changing a display field.
